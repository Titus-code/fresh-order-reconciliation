# 生鲜批发订单与对账小工具

创建日期：2026-10-06  
当前状态：项目规划，尚未实现。

## 1. 项目要解决什么问题

以家庭生鲜超市的真实业务类型为背景：向镇上及周边餐饮店后厨、学校和医院食堂批发配送蔬菜、粮油等商品。

本项目从现在开始搭建，先使用模拟数据。目标是将订单、实际交付、退货和回款整理成一份可核对的账单，回答四个问题：

1. 每个客户在本期收到了哪些货，应付多少钱？
2. 已收到多少货款，还有多少未结清？
3. 哪些原始记录有重复、缺失或金额异常，需要人工确认？
4. 如何用 Excel、Python 和 SQL 得出一致的结果？

这是一个业务数据处理案例。重点是流程完整、金额正确、结果可追溯，先不做复杂管理系统。模拟数据和新做的工具不写成过去已经上线的经营成果。

## 2. 第一版范围

**处理流程：原始数据 → 检查与异常清单 → 有效订单及回款 → 客户对账汇总 → 一页结果说明。**

第一版完成：

- 商品和客户信息匹配。
- 订单明细核对，按实际交付数量和退货计算净应收。
- 按订单匹配回款，汇总客户应收、已收和未结清金额。
- 导出可追溯的异常记录，不把错误数据悄悄删掉。
- Excel、Python、SQL 三种结果相互核对。

第一版暂不处理：完整库存、供应商采购结算、税务开票、配送路线、多用户权限、复杂网页后台。也不计算缺少采购成本依据的毛利。

默认一个订单只对应一个客户和一次交付；多次配送可以拆成不同订单。一笔回款只关联一个订单，一张订单可以多次回款。跨订单分摊、退款和预收款管理留到后续扩展。

## 3. 建议使用的工具

| 工具 | 在本项目中的用途 |
| --- | --- |
| Excel | XLOOKUP 匹配信息、检查明细、透视表汇总，制作人工核对样本 |
| Python / pandas | 读取文件、检查字段、识别重复和异常、关联与汇总、导出结果 |
| MySQL | 存储清洗后的有效数据，用 SQL 生成订单及客户汇总 |
| Markdown 或 HTML 网页 PPT | 展示业务问题、处理流程、关键结果和局限 |

可以使用 AI 辅助代码、SQL、排版和排错。自己需要能够解释数据含义、计算规则，并通过手工样本确认结果。NumPy 按实际需要使用，不为展示工具数量强行加入。

## 4. 模拟数据设计

建议先手工建一个小样本，跑通后再扩展到约 5 个客户、10 个商品、50 笔订单。数量是练习目标，不是已经完成的成果。所有文件注明“模拟数据”，不使用真实客户名称、联系方式或账款。

### 四张输入表

| 文件 | 一行代表什么 | 必需字段 |
| --- | --- | --- |
| `customers.csv` | 一个客户 | `customer_id`、`customer_name`、`customer_type` |
| `products.csv` | 一个固定规格的商品 | `product_id`、`product_name`、`specification`、`unit` |
| `order_lines.csv` | 一张订单中的一条商品明细 | `order_id`、`line_no`、`customer_id`、`order_date`、`product_id`、`unit`、`ordered_qty`、`delivered_qty`、`returned_qty`、`unit_price` |
| `payments.csv` | 一笔分配给订单的回款 | `payment_id`、`order_id`、`payment_date`、`amount` |

数据约定：

- 编号按文本保存，避免前导零丢失；日期使用 `YYYY-MM-DD`。
- `order_id + line_no` 唯一确定一条订单明细，`payment_id` 唯一确定一笔回款。
- 同一订单的客户和订单日期必须一致。同一商品可以出现在多笔订单中，不能仅按商品编号去重。
- 商品固定规格和单位：例如“食用油 5L/桶”和“食用油 10L/桶”使用不同商品编号。
- `unit_price` 为订单当时的成交单价。XLOOKUP 可以补商品名称、规格和单位，不能用今天的价格覆盖历史成交价。
- 回款金额必须为正；退款、负数冲销暂不自动处理，列入待人工确认事项。

### 先明确金额口径

```text
交付金额 = 实际交付数量 × 成交单价
退货金额 = 退货数量 × 成交单价
明细净应收 = 交付金额 - 退货金额
订单净应收 = 该订单所有有效明细净应收之和
订单已收 = 该订单有效回款金额之和
订单余额 = 订单净应收 - 订单已收
```

- 按实际交付数量计费；下单但未交付的部分不计入应收。
- 第一版只接受 `0 ≤ returned_qty ≤ delivered_qty ≤ ordered_qty`，其他情况交人工核查。
- 数量与单价的单位必须一致。第一版发现“斤”和“公斤”等不一致时先报异常，不猜测换算；袋和桶也不能在没有规格依据时折算。
- 金额使用十进制定点运算，例如 Python `Decimal` 和 MySQL `DECIMAL`；交付金额、退货金额分别按四舍五入保留两位小数，再计算明细净应收，三种工具采用同一规则。
- 订单余额小于 0 表示超额回款或数据问题，保留负值并标记，不直接截断为 0。
- 日期口径统一：先选取本期订单，再统计这些订单截至指定对账日的回款。本期以前的订单余额暂不纳入，不把这个汇总称为客户全部历史欠款。

### 必须先手算通过的例子

客户 A 的一张模拟订单：

| 商品 | 下单数量 | 实际交付 | 退货 | 单价 | 净应收 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 土豆 | 10 公斤 | 10 公斤 | 2 公斤 | 4 元/公斤 | 32 元 |
| 食用油 5L/桶 | 2 桶 | 2 桶 | 0 桶 | 60 元/桶 | 120 元 |

订单净应收为 **152 元**。两次回款分别为 60 元和 40 元，合计 **100 元**，余额应为 **52 元**。Excel、Python 和 SQL 必须得到相同结果。

## 5. 异常处理与验收

每条异常输出来源文件、来源行号、订单或回款编号、错误类型和说明；原始文件保留不动。

| 情况 | 预期处理 |
| --- | --- |
| 订单明细主键重复，内容相同 | 标记重复，保留一份参与计算；报告排除数量 |
| 订单明细主键相同，内容冲突 | 标记冲突，整张订单暂缓出正式账单 |
| 客户或商品不存在、必填字段缺失 | 列为异常，相关订单暂缓出正式账单 |
| 同一订单出现不同客户 | 标记归属冲突，禁止自动合并 |
| 单位不一致、退货大于交付、数量或价格非法 | 列为异常，相关订单暂缓出正式账单 |
| 重复回款编号 | 相同内容只计一次；冲突内容暂缓计入并标记订单待复核 |
| 回款关联不存在的订单 | 输出未匹配回款，不丢弃、不随意归属客户 |
| 部分回款、分次回款 | 正确求和，余额保留未结清部分 |
| 回款日期晚于对账日 | 不计入本次已收，单独记录被截止日期排除 |
| 超额回款 | 保留负余额，标记待复核 |

对有阻断异常的订单，其全部明细与关联回款从“可确认账单”中暂缓，不只剔除坏行后把剩余部分当完整订单。客户汇总列出暂缓订单数；有暂缓项时标注“部分数据待确认”。

**关联表时最容易出错的一点：** 一张订单有多行商品，也可能有多笔回款。先分别把商品明细和回款汇总到“一行一个订单”，再关联。直接把两张明细表按订单编号连接，会重复累计金额。

## 6. 按这个顺序搭建

- [ ] **第一步：写清口径。** 确定字段、单位、金额计算及对账截止日期，先完成上面的手工样本。
- [ ] **第二步：制作输入数据。** 建立四张模拟数据表，加入正常订单及已知异常，另存预期结果。
- [ ] **第三步：做 Excel 原型。** 完成信息匹配、金额计算和客户汇总，能够逐笔追溯。
- [ ] **第四步：写 Python 流程。** 实现读取、校验、异常报告、有效数据汇总及结果导出；运行一次能够重建输出。
- [ ] **第五步：补 SQL。** 将有效数据导入 MySQL，用订单级汇总再关联的方式生成相同结果。
- [ ] **第六步：交叉核对。** 检查手工样本与全部异常案例，记录输入笔数、暂缓笔数、有效笔数及金额差异。
- [ ] **第七步：做简短展示。** 一页结果说明，配少量截图或 3-5 页 HTML 网页 PPT。
- [ ] **第八步：独立复现。** 换一份输入，跑出结果并解释异常。

先完成最小版本，不急着做网页界面或扩大数据量。
