# 生鲜批发订单与对账数据处理

把生鲜批发配送业务里散落的订单明细、实际交付、签收退货和回款流水，整理成一份能逐笔追溯的客户对账结果，并让 **Excel、Python、SQL 三条路径算出完全一致的数字**。

场景取自真实的批发配送业务类型：向本地餐饮门店后厨及学校、医院食堂配送蔬菜、粮油等农副产品，按自然月结账、次月 10 日前付款。样本数据按真实业务节奏构造（固定随机种子生成，每行带 `is_simulated` 标识），不含任何真实客户名称、联系方式或账款信息。

| 规模 | 数值 |
| --- | ---: |
| 客户 | 6 家（粉面店、家常菜馆、快餐店、乡村饭店、小学食堂、医院食堂） |
| 固定规格商品 | 20 种（15 种蔬菜、鸡蛋、籼米、小麦粉、菜籽油、大豆油） |
| 供货期间 | 2026-09-01 至 2026-09-30，完整自然月 |
| 订单 / 明细 | 143 张 / 966 行 |
| 收款流水 / 订单分配 | 7 笔 / 100 条 |
| 9 月净应收 | **44,914.30 元** |
| 截至 2026-10-06 已收 / 未结清 | **26,254.15 元 / 18,660.15 元** |

## 1. 业务问题

批发配送的账目有几个天然难点。下单量和实际到货量经常差一点，叶菜损耗、临时缺货都会造成少送；客户当场挑拣退货，退货量要按当天成交价冲减，不能按现行价格；回款是整笔打的，一笔转账覆盖多张订单，需要拆到订单级才能算出某张单子到底结清没有；每家客户结账周期和付款习惯还不一样。

所以一份能用的月账单必须回答四个问题：

1. 每个客户本月实际收到多少货，应付多少钱？
2. 已经收到多少钱，还有多少没结清？
3. 哪些原始记录有重复、缺失或金额异常，需要人工确认？
4. 用 Excel、Python、SQL 分别算一遍，结果能不能对上？

这是一次业务数据处理实践。重点在流程完整、金额正确、结果可追溯，不做复杂的库存或订单管理系统。

## 2. 金额口径

全部计算遵循同一套口径，三条实现路径共用：

```text
交付金额   = 实际交付数量 × 成交单价
退货金额   = 签收退货数量 × 成交单价
明细净应收 = 交付金额 - 退货金额        （两个金额各自四舍五入到分，再相减）
订单净应收 = 该订单所有有效明细净应收之和
订单已收   = 该订单有效回款金额之和
订单余额   = 订单净应收 - 订单已收
```

几条不能含糊的约定：

**按下单量还是按交付量计费？** 按实际交付量。下单 10.1 公斤只到货 9.6 公斤，那 0.5 公斤不该收钱。这直接影响收入确认，是这套账里最容易被做错的一处。

**退货怎么算？** 用**成交当时的单价**冲减，不能用商品表里的当前价。价格随周次小幅波动，用错价格会让整月的退货金额偏差。

**金额用什么类型存？** 全程十进制定点，绝对不碰浮点数。Python 用 `Decimal`，MySQL 用 `DECIMAL(10,2)`，Excel 用 `ROUND`，三者规则一致：先分别对交付金额、退货金额四舍五入到分，再相减得到明细净额。

**回款按哪个口径统计？** `receipts.csv` 是收款流水（整笔到账），`payments.csv` 是这笔钱分配到各订单的明细。这两个是**同一笔钱的两种视角，不能相加**。两者各自汇总的已收总额必须相等，这是对账的首要校验项。

**要不要固定资产总额？** 不要。`order_lines.csv` 里没有任何总计行、合并单元格或小计，从源头上杜绝重复累计。

## 3. 处理流程

```text
原始 CSV  →  字段与业务规则校验  →  异常清单（问题数据不静默丢弃）
                 ↓
         有效订单明细  →  汇总到订单级  →  关联回款  →  客户对账汇总
                                                          ↓
                                              订单对账表 / 客户汇总表 / 异常明细表
```

关键设计：**先把明细和回款各自汇总到"一行一个订单"，再关联。** 一张订单有多行商品、也可能有多笔回款，如果直接把两张明细表按订单号连接，金额会成倍重复。这是订单对账里最容易踩的结构性错误。

异常数据不删除，全部输出到 `exceptions_*.csv`，注明来源文件、行号、业务编号、错误类型和说明，原始文件保持不动。对存在阻断异常的订单，**整张订单**从可确认账单中暂缓，而不是只剔除坏行、把剩下的残行当成完整订单。

这里有一个口径细节值得说明：对账截止日会**排除**截止日之后到账的回款。截至 9 月 30 日时，有 84 条分配记录因为到账日（10 月 2—6 日）晚于截止日而被排除。这些记录不是数据错误，只是不在本次统计窗口内，但它们同样会被输出到异常清单里，所以 9 月 30 日那次运行显示"异常 84 条"、而 10 月 6 日那次是"异常 0 条"。做对账必须把**数据质量问题**和**口径排除**分开看，否则会误判数据健康度。

## 4. 三路实现与交叉验证

### 数据生成与独立检查（`scripts/`）

`generate_sample_data.py` 用固定种子 `20260906` 生成全部样本，并计算每个文件的 SHA-256 写入 `manifest.json`，拒绝覆盖已有快照。`check_sample_data.py` 是**独立**的验证脚本：它不引用生成器的任何函数，而是从落盘 CSV 重新读取，把数量换算成"十分之一公斤"整数、金额换算成"分"整数，用纯整数运算重算全部订单、客户、流水和两个截止日期的结果。

```
PASS: 143 orders; 966 lines; 100 allocations; 7 receipts; 2 cutoffs.
```

### Python 对账流程（`src/reconcile.py`）

读取 `data/raw/`，校验字段完整性、主键唯一性、客户与商品存在性、单位一致性、数量关系、单价区间，然后汇总订单、关联回款、导出三份结果 CSV。

```
$ python src/reconcile.py --cutoff 2026-10-06
对账截止日 2026-10-06
有效订单 143 张，明细 966 行，暂缓订单 0 张
净应收 44914.30 元，已收 26254.15 元，未结清 18660.15 元
异常 0 条
```

### SQL（`sql/`）

`schema.sql` 是 MySQL 8.0 建表脚本，含主键、索引、外键和 `CHECK` 约束（`0 ≤ returned_qty ≤ delivered_qty ≤ ordered_qty`）。`queries.sql` 含 11 条查询，覆盖明细净额、订单对账、客户汇总、五类异常检查和总账核对。

`verify_sqlite.py` 把同一份 SQL 在 SQLite 里跑一遍做交叉验证，自动改写 `CREATE OR REPLACE VIEW` 和 `@cutoff` 两处引擎差异，不改动 `queries.sql` 本身。

```
[Q5 客户对账汇总]  与 expected 对比：PASS 全部一致
[Q6 主键重复]        共 0 行
[Q7 数量、单位、金额不合规]  共 0 行
[Q8 回款关联异常]    共 0 行
[Q9 流水与分配金额相符]  共 0 行
[Q10 receipts 流水口径]  26254.15
[Q10 payments 分配口径]  26254.15
SQL 总计净应收 44914.30 元
```

两个引擎、三条路径，同一份数据，金额精确到分完全一致。

## 6. 两个真实踩到的坑

这部分是这套代码里最有价值的东西，也是精度问题的实际教训。

### 坑一：SQLite 的 NUMERIC 亲和性

金额列如果按 `NUMERIC` 建表，SQLite 会把 `'4.60'` 转成浮点数。`CAST('4.60' AS REAL) * 100 = 459.99999999999994`，截断成整数就是 **459**，每行少一分，整月汇总差了 **8.13 元**（44,906.17 vs 44,914.30）。这种误差不会报错，只会让账单少收钱。

解决方案是彻底绕开浮点：把数量、金额列在 SQLite 里声明为 `TEXT` 原样保存，所有换算走字符串去小数点，全程整数运算。

```sql
-- 数量 '10.1' → 101（十分之一公斤），金额 '3.40' → 340（分）
CAST(REPLACE(delivered_qty, '.', '') AS INTEGER)
  * CAST(REPLACE(unit_price, '.', '') AS INTEGER)
```

明细净额 = `(交付量×10 × 单价×100 + 5) / 10`，整数除法天然等于四舍五入到分，与 Python `Decimal(ROUND_HALF_UP)` 和 Excel `ROUND` 完全一致。

### 坑二：TEXT 列的比较是按字符逐位比的

改成 `TEXT` 之后，异常检查脚本开始报出 1 条假异常："交付大于下单"。核查原始数据，那一行是下单 10.1、交付 9.6——交付明明**小于**下单。

原因是 `'9.6' > '10.1'` 这个字符串比较返回真，因为 `'9'`（0x39）排在 `'1'`（0x31）后面。文本比较不看数值大小，只看字符顺序。

修好这个之后，同类问题在商品表的价格区间检查上又出现一次：价格下限列如果仍是 `NUMERIC`，`'2.30'` 会变成浮点 `2.3`，去小数点后得到 `23`，和明细里的 `230` 一比，**966 行全部误报"单价超出区间"**。

结论很清楚：**只要一个字段通过字符串去掉小数点来换算，它就必须以字符串形式贯穿到底**，任何一层引入数值亲和性都会污染后续所有比较。这两个坑都是先跑出错误结果、再逐层定位才发现的，不是靠代码审查看出来的。

## 8. 运行方式

仅依赖 Python 3.10+ 标准库，无需安装第三方包。

```bash
python scripts/check_sample_data.py                      # 独立校验样本金额
python scripts/generate_sample_data.py --output-dir data-rebuilt   # 重新生成样本
python -m unittest discover -s tests -v                  # 正常与脏数据回归测试
python src/reconcile.py --cutoff 2026-10-06              # 出对账结果
python sql/verify_sqlite.py --cutoff 2026-10-06          # 用 SQL 复核一遍
python src/reconcile.py --cutoff 2026-09-30              # 换截止日复现
```

生成器不覆盖已有数据文件，换假设时请输出到新目录，原始快照保留不动。

## 9. 数据设计要点

完整场景设定、价格区间依据和参考资料见 [数据说明与字段口径](docs/sample-data.md)。

样本覆盖了真实业务里各种正常发生的情况：**50 行少送、27 行签收退货**（两类可能重叠），以及全额付款、部分付款、分次付款、暂未付款和月末后收到本期货款。医院食堂 10 月 5 日支付 5,000 元、小学食堂 9 月 30 日支付 5,000 元，都是部分付款，用来验证余额保留的正确性。

少送和合理退货属于**业务情况，不是脏数据**，绝不能当异常删掉——它们直接决定应收金额。这一点在代码里体现为：数量关系违反 `0 ≤ 退货 ≤ 交付 ≤ 下单` 才报异常，合理范围内的少送只是照实计费。

商品固定规格与计价单位绑定：食用油 5 升桶和 10 升桶如果是不同规格，就是不同商品编号，不能靠换算折算。遇到"斤"和"公斤"不一致时先报异常交人工确认，不猜换算率。袋、桶类商品数量都是整数。

当前正式快照是**干净的正常账**，没有人为混入重复主键、未知商品或非法数量，所以正式异常清单返回 0 条。异常处理逻辑由 `tests/fixtures/dirty/` 和标准库回归测试覆盖：坏明细会暂缓整单，正常订单仍可出账。
