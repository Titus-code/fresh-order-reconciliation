## 第 1 步：明细计算表 `calc_lines`

新建工作表，命名 `calc_lines`。这是整个原型的核心，966 行明细的净应收都在这里算出来。

### 1.1 引用原始列（A—L 列）

在 A1 敲表头，A2 起用公式引用原始表：

| 列 | 表头 | A2 单元格公式 |
| --- | --- | --- |
| A | order_id | `=raw_order_lines!A2` |
| B | line_no | `=raw_order_lines!B2` |
| C | customer_id | `=raw_order_lines!C2` |
| D | order_date | `=raw_order_lines!D2` |
| E | product_id | `=raw_order_lines!E2` |
| F | unit | `=raw_order_lines!F2` |
| G | ordered_qty | `=raw_order_lines!G2` |
| H | delivered_qty | `=raw_order_lines!H2` |
| I | returned_qty | `=raw_order_lines!I2` |
| J | unit_price | `=raw_order_lines!J2` |
| K | delivery_note | `=raw_order_lines!K2` |
| L | is_simulated | `=raw_order_lines!L2` |

选中 A2:L2，向下填充到**第 967 行**（966 条明细 + 表头）。

### 1.2 用 XLOOKUP 补商品和客户信息（M—O 列）

| 列 | 表头 | 公式 | 说明 |
| --- | --- | --- | --- |
| M | product_name | `=XLOOKUP($E2,dim_products!$A$2:$A$21,dim_products!$B$2:$B$21,"未找到")` | 按商品编号取名称 |
| N | specification | `=XLOOKUP($E2,dim_products!$A$2:$A$21,dim_products!$C$2:$C$21,"未找到")` | 取固定规格 |
| O | customer_name | `=XLOOKUP($C2,dim_customers!$A$2:$A$7,dim_customers!$B$2:$B$7,"未找到")` | 按客户编号取名称 |

XLOOKUP 最后一个参数是"找不到时返回什么"。这里填 `"未找到"`，等于自带一个异常检查——如果哪一行显示"未找到"，说明明细里出现了商品表或客户表里没有的编号。**不要**用 `IFERROR` 把它藏起来。

### 1.3 金额计算（P—R 列）——整个原型的核心

| 列 | 表头 | 公式 |
| --- | --- | --- |
| P | gross_amount | `=ROUND($H2*$J2,2)` |
| Q | return_amount | `=ROUND($I2*$J2,2)` |
| R | net_amount | `=$P2-$Q2` |

这里有一个**必须理解、面试大概率会问**的细节：为什么 P 和 Q 各自 `ROUND` 到分，而不是算完 `=ROUND(H2*J2-I2*J2,2)`？

因为业务口径是"交付金额、退货金额**分别**四舍五入到分，再相减"。两种算法在个别行会差一分钱。Python 侧用的是 `Decimal(...).quantize(0.01, ROUND_HALF_UP)` 分别取整，SQL 侧用的是整数分运算，都遵循"分别取整再相减"。三边要一致，Excel 就必须照同样的顺序算。这也是为什么 P、Q 要对客户可见，而不能合成一列——否则你没法核查。

**按下单量还是交付量计费？** 看 P 列用的是 H（`delivered_qty`，实际交付）而不是 G（`ordered_qty`，下单量）。少送的部分不该收钱，这是这套账最容易被做错的一处。

### 1.4 异常检查列（S—V 列）

| 列 | 表头 | 公式 |
| --- | --- | --- |
| S | 数量异常 | `=IF(OR($I2>$H2,$H2>$G2,$G2<=0),"数量关系异常","")` |
| T | 单位异常 | `=IF($F2<>XLOOKUP($E2,dim_products!$A$2:$A$21,dim_products!$D$2:$D$21,""),"单位不一致","")` |
| U | 单价异常 | `=IF(OR($J2<XLOOKUP($E2,dim_products!$A$2:$A$21,dim_products!$F$2:$F$21,0),$J2>XLOOKUP($E2,dim_products!$A$2:$A$21,dim_products!$G$2:$G$21,99999)),"单价越界","")` |
| V | 主键重复 | `=IF(COUNTIFS($A$2:$A$967,$A2,$B$2:$B$967,$B2)>1,"主键重复","")` |

S 列的判断依据是业务不变式 `0 ≤ 退货 ≤ 交付 ≤ 下单`。**注意少送本身不是异常**——下单 10.1、交付 9.6 完全合法，照实计费就行；只有当退货超过交付、或交付超过下单时才是数据错误。这个区分很重要，别把正常的业务波动当成脏数据删掉。

### 1.5 核对点（做完这一步先停下来对）

| 检查项 | 怎么做 | 应该是 |
| --- | --- | --- |
| 明细行数 | `=COUNTA($A$2:$A$967)` | **966** |
| 有没有"未找到" | `=COUNTIF($M$2:$O$967,"未找到")` | **0** |
| 有没有异常 | `=COUNTIF($S$2:$V$967,"?*")` | **0** |
| 净应收合计 | `=ROUND(SUM($R$2:$R$967),2)` | **44914.30** |

**最后这个数 44,914.30 是关键。** 它必须和 Python、SQL 的结果一致。对不上就先别做下一步，回头查——最常见的原因是某列少填充了几行、或者 ROUND 的位置放错了。

## 第 2 步：订单对账表 `calc_orders`

明细是按商品拆开的，账单要按订单出。新建工作表 `calc_orders`。

### 2.1 取订单编号列表

订单编号列可以从 `order_summary.csv` 里取，或者用更快的方法：把 `calc_lines` 的 A 列复制到新表，然后 **数据 → 删除重复项**，得到 143 个唯一订单编号。

| 列 | 表头 | 公式 |
| --- | --- | --- |
| A | order_id | （143 个唯一编号，A2 起） |
| B | customer_id | `=XLOOKUP($A2,calc_lines!$A$2:$A$967,calc_lines!$C$2:$C$967,"未找到")` |
| C | customer_name | `=XLOOKUP($A2,calc_lines!$A$2:$A$967,calc_lines!$O$2:$O$967,"未找到")` |
| D | order_date | `=XLOOKUP($A2,calc_lines!$A$2:$A$967,calc_lines!$D$2:$D$967,"")` |
| E | line_count | `=COUNTIF(calc_lines!$A$2:$A$967,$A2)` |
| F | net_receivable | `=ROUND(SUMIF(calc_lines!$A$2:$A$967,$A2,calc_lines!$R$2:$R$967),2)` |
| G | received | `=ROUND(SUMIFS(fact_payments!$D$2:$D$101,fact_payments!$B$2:$B$101,$A2,fact_payments!$C$2:$C$101,"<="&截止日)/1,2)` |
| H | balance | `=$F2-$G2` |
| I | status | `=IF($H2=0,"已结清","未结清")` |

**G 列是关键，用 SUMIFS 而不是 SUMIF。** 它要同时满足两个条件：回款属于这张订单（`order_id` 匹配），且**到账日期不晚于对账截止日**（`payment_date <= 截止日`）。第二个条件就是对账截止日的口径——截至 9 月 30 日时，10 月 2 日到账的钱不能算进来。

`截止日` 三个字是一个**命名单元格**。在任意空白格（比如 `K1`）填 `2026-10-06`，然后选中它，在左上角名称框里输入"截止日"回车。这样以后换截止日只需改这一个格子，不用改 143 行公式。

### 2.2 核对点

| 检查项 | 公式 | 应该是 |
| --- | ---: | ---: |
| 订单数 | `=COUNTA($A$2:$A$144)` | **143** |
| 明细行数合计 | `=SUM($E$2:$E$144)` | **966** |
| 净应收合计 | `=ROUND(SUM($F$2:$F$144),2)` | **44914.30** |
| 已收合计（截止 10-06） | `=ROUND(SUM($G$2:$G$144),2)` | **26254.15** |

明细行数合计必须是 966——这证明 143 张订单没有丢行也没有重复计入。

**换截止日测一次**：把"截止日"格改成 `2026-09-30`，G 列合计应变成 **6000.00**，未结清变成 **38914.30**。再改回 `2026-10-06`。这个动作验证了跨月回款的截止口径是活的，不是写死的——面试时这是个很好的演示点。

## 第 4 步：数据透视表 `pivot_report`

上面三步用的是公式，透视表是另一条独立的汇总路径——两条路径得出同一个数，才叫交叉验证。新建工作表 `pivot_report`，选中 `calc_lines` 的数据区域，**插入 → 数据透视表**。

**透视表一：客户级净应收**

- 行：`customer_name`
- 值：`net_amount` 求和（数字格式设成两位小数）
- 结果应与第 3 步的 D 列逐行一致

**透视表二：商品级配送量**

- 行：`product_name`
- 值：`delivered_qty` 求和
- 用途是核对单品总量，面试时可以用来讲"哪种菜走量最大"

**透视表三：按日期看少送情况**

- 行：`order_date`
- 值：`delivered_qty` 求和、`ordered_qty` 求和
- 再加一个计算字段或辅助列算差额，用来看少送集中在哪些天

如果透视表的净应收合计和公式算出的 44,914.30 不一致，通常是透视表把 `raw_order_lines` 也选进去了导致重复计数，或者数据区域少框了行。

## 第 5 步：异常清单 `exceptions`

新建工作表 `exceptions`。把 `calc_lines` 的 S—V 四个检查列筛出非空值，复制到这里。当前这份样本是**干净的正常账**，所以应该是**空表**——这本身是正确的验证结果。

但为了让这个页签不是空的，**建议你手工造几条脏数据来测**（先备份 `对账原型.xlsx`）：

1. 复制 `raw_order_lines` 的某一行，粘到表尾（制造重复主键，V 列应报"主键重复"）
2. 找一行把 `unit` 从"公斤"改成"斤"（T 列应报"单位不一致"）
3. 找一行把 `returned_qty` 改成大于 `delivered_qty` 的值（S 列应报"数量关系异常"）

这三条改完，异常清单应该出现 3 条记录，且净应收合计会变化——这就是"异常数据会影响账单"的直观演示。测完把改动撤销，恢复成干净状态。

面试时这段很有价值：你能说清**异常怎么被发现的、发现后怎么处理**（对应 README 里"整张订单暂缓出账"的规则），而不只是说"我会做透视表"。

## 面试时怎么讲这段（3 分钟版）

> 这是一个批发配送的对账练习项目，用模拟数据做的，966 行订单明细、143 张订单、6 家客户。核心是把订单、实际交付、签收退货和回款整理成一份能逐笔追溯的月账单。
>
> 金额口径上有几个关键决定：一是**按实际交付量计费，不按下单量**，因为少送的部分不该收钱；二是退货用**成交当时的单价**冲减，不能用当前价；三是**金额全程用十进制定点**，Excel 用 ROUND、Python 用 Decimal、SQL 用整数分，三边结果精确一致。
>
> 过程中真踩到过精度问题。SQLite 的 NUMERIC 亲和性会把 `4.60` 转成浮点，乘 100 得到 `459.99999999999994`，截断后每行少一分，整月差了 8 块多。后来改成整数分运算才解决。改成文本列之后又踩到第二个坑：文本比较是按字符逐位比的，`9.6` 大于 `10.1` 会返回真，导致异常检查报假警报。最后的结论是——凡是用"去掉小数点"做换算的字段，必须全程以字符串贯穿到底。
>
> 另外我把**数据质量问题和口径排除分开看**。截至 9 月 30 日那次，有 84 条回款因为到账日在截止日之后被排除，这不是数据错误，但会出现在异常清单里，所以两次运行的异常条数不一样。做对账如果不区分这两类，会误判数据健康度。
